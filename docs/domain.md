# Доменная модель первого релиза

Статус: целевая модель согласована. CRUD и жизненный цикл до оплаты реализованы;
попытки оплаты, подтверждение адреса и blockchain-интеграция — следующий этап.

## Границы

Сервис выставляет счета и проверяет оплату в тестовой блокчейн-сети.
Один счёт оплачивается одним переводом точной суммы. Частичные оплаты
не суммируются, переплата не засчитывается автоматически. Товары и услуги
пока описываются свободным текстом. Escrow добавляется следующим этапом.

Прикладные данные хранятся в PostgreSQL. Блокчейн является источником
подтверждения перевода. Сервер не хранит приватные ключи покупателя.

## Счёт

| Поле | Назначение |
| --- | --- |
| `id` | Уникальный идентификатор |
| `description` | Назначение платежа |
| `amount` | Положительная целая сумма минимальных единиц токена |
| `chain_id` | Сеть оплаты |
| `token_address` | Контракт токена |
| `recipient_address` | Получатель |
| `status` | `draft`, `open`, `paid`, `expired`, `cancelled` |
| `expires_at` | Срок оплаты |
| `created_at`, `updated_at` | Время создания и изменения |
| `issued_at`, `cancelled_at`, `paid_at` | Время соответствующих переходов |

Суммы передаются через API строками и сохраняются в PostgreSQL как целые
значения `NUMERIC` без дробной части. Вычисления через `float` запрещены.
Время хранится в UTC с часовым поясом (`timestamptz`).

### Переходы

| Из | В | Условие |
| --- | --- | --- |
| — | `draft` | Создание |
| `draft` | `open` | Выставление валидного счёта |
| `draft` | удалён | Удаление черновика |
| `open` | `paid` | Подтверждён подходящий перевод |
| `open` | `expired` | Истёк срок оплаты |
| `open` | `cancelled` | Отмена продавцом |
| `expired` | `paid` | Позже подтверждён перевод, совершённый вовремя |
| `cancelled` | `paid` | Позже подтверждён перевод, совершённый до отмены и срока оплаты |

Полный CRUD доступен для черновиков. После выставления сумма, сеть,
токен и получатель неизменны. Исправление условий требует нового счёта.
Оплаченные счета не удаляются и не редактируются произвольно.

Своевременность определяется временем блока перевода, а не моментом
проверки worker. Перевод должен попасть в интервал от выставления счёта
включительно до срока оплаты или отмены (более ранней границы) исключительно.
Точный источник времени и пограничные случаи часов приложения и сети
нужно проверить при реализации интеграции.

`paid_at` означает время признания оплаты сервисом. Время перевода хранится
отдельно в данных попытки. Состояние «подтверждается» в интерфейсе выводится
из попытки оплаты; счёт при этом ещё не считается оплаченным.

## Попытка оплаты

У счёта может быть несколько попыток. Ошибка попытки не закрывает счёт.

Основные поля: `id`, `invoice_id`, `tx_hash`, `status`, `reason`,
`block_number`, `block_hash`, `block_timestamp`, `log_index`,
`last_checked_at`, `next_check_at`, `created_at`, `updated_at`.

Состояния: ожидает проверки, подтверждается, принята, отклонена.
Недоступность RPC сохраняется как временная ошибка проверки и приводит
к повторной попытке, а не к отклонению платежа. Для дополнительных и поздних
переводов нужен явный признак необходимости разбора.

### Проверка

1. Покупатель подписывает перевод в кошельке и передаёт хеш через API.
2. API сохраняет попытку и отвечает без ожидания подтверждения блокчейна.
3. Worker проверяет сеть, успешность транзакции и событие перевода:
   контракт токена, плательщика, получателя, сумму и время.
4. Worker ожидает выбранное для сети условие подтверждения.
5. В одной транзакции PostgreSQL принимается оплата, меняется состояние
   счёта и добавляется событие истории.

Хеш от браузера не является доказательством оплаты. Предполагается закрепить
адрес плательщика при начале оплаты с подтверждением владения подписью
сообщения. Проверяем адрес отправителя события перевода. Обычный перевод
токена не содержит `invoice_id`; ограничения сопоставления одинаковых счетов
нужно явно учесть. Собственный платёжный контракт может решить это позже.

Повторная отправка того же хеша для того же счёта возвращает существующую
попытку. Уникальность принятого перевода по `(chain_id, tx_hash, log_index)`
исключает его зачёт по нескольким счетам. Проверка и принятие должны быть
безопасны при конкурентной работе нескольких worker.

Неверный токен, получатель или сумма не засчитываются. Переводы после срока
или отмены, а также дополнительные переводы по оплаченному счёту сохраняются
для разбора без автоматического возврата. Отклонение попытки приложением
не отменяет состоявшийся перевод в блокчейне.

## Событие счёта

Поля: `id`, `invoice_id`, `type`, `occurred_at`, необходимые детали.
Примеры: создание, выставление, получение хеша, отмена, истечение срока,
подтверждение оплаты. История выставленных счетов только дополняется.
Изменение статуса и соответствующее событие записываются атомарно.
Удаление черновика может удалять его техническую историю.

## До начала реализации

- Проверить доступность тестовой сети, RPC и faucet; Base Sepolia и USDC
  пока являются кандидатами.
- Выбрать условие подтверждения и поведение при реорганизации цепочки.
- Спроектировать доступ продавца и покупателя, подпись сообщения с защитой
  от повторного использования и привязку плательщика к счёту.
- Уточнить поиск переводов, если браузер закрылся до отправки хеша.
- Установить сроки повторной проверки неизвестных транзакций.
- Определить API и ограничения базы для атомарного, повторяемого зачёта.
