# Отчёт: сервис платёжных счетов в блокчейне

## Доменная область и границы реализации

Сервис управления счетами для будущей оплаты токенами в блокчейне.

Реализованный этап: кабинет одного продавца, CRUD черновиков, выставление,
отмена, истечение срока и история изменений. 

Платёжная интеграция и escrow
относятся к следующим этапам. 
**Сейчас сервис не проверяет транзакции,
не подключает кошелёк и не принимает реальные средства.**

## Стек

Go, стандартный net/http, PostgreSQL 17, pgx, HTML/CSS/JavaScript без
frontend runtime, Docker Compose. Наблюдаемость: zap, OpenTelemetry,
Prometheus, Grafana, Loki, Tempo и Grafana Alloy.

**Архитектура:** модульный монолит с упрощённой гексагональной архитектурой.
Порт хранения находится в `internal/service`, адаптер — в `internal/repository`.
Домен не зависит от транспорта, базы или инструментов наблюдаемости.
Один исполняемый файл запускается как API, worker или процесс миграции.

## Основные сущности

**Счёт:** назначение платежа, целая сумма минимальных единиц токена, сеть,
токен, получатель, срок, статус, версия и временные отметки.
Полный CRUD — для черновиков. Условия выставленного счёта неизменны.

**Событие счёта:** тип изменения, время и версия счёта. История сохраняется
атомарно с состоянием; удаление черновика удаляет его техническую историю.

**Попытка оплаты:** запланированная сущность, ещё не реализована.
Статус `paid` зарезервирован в модели, но доступного перехода в него пока нет.

## 12 факторов

| Фактор | Реализация и доказательство |
| --- | --- |
| 1. Кодовая база | Один Git-репозиторий для приложения, миграций, UI и конфигурации. Окружения используют одну кодовую базу. Начальный коммит и push выполняет владелец проекта. |
| 2. Зависимости | `go.mod` задаёт версии, `go.sum` проверяет содержимое модулей. Dockerfile фиксирует версии Go и базовых образов. Статический бинарник не зависит от установленного Go на хосте. Образы закреплены тегами, а не digest: строгая побитовая воспроизводимость требует дальнейшего закрепления digest. |
| 3. Конфигурация | DATABASE_URL, PORT, LOG_LEVEL, WORKER_INTERVAL и OTEL_EXPORTER_OTLP_ENDPOINT читаются из окружения. `.env` игнорируется Git и Docker build context; `.env.example` содержит только локальные демонстрационные значения. |
| 4. Внешние службы | PostgreSQL подключается через DATABASE_URL; экспорт трейсов — через OTLP endpoint. Логи и метрики собираются внешними процессами. Переключение совместимых экземпляров не требует изменения бизнес-кода. |
| 5. Сборка, релиз, запуск | Multi-stage Dockerfile компилирует бинарник и встраивает UI. RELEASE_VERSION задаёт тег образа и версию в логах. Запуск использует готовый бинарник. Изменения кода требуют новой сборки; релиз — фиксированный образ плюс конфигурация. Учебный тег dev переиспользуется локально; для релизов нужно задавать уникальный RELEASE_VERSION и сохранять конфигурацию. |
| 6. Процессы | Счета, события и сроки находятся в PostgreSQL. API и worker не используют локальный диск как долговременное хранилище. Контейнеры приложения запускаются с read_only. Локальные очереди телеметрии не являются источником бизнес-данных. |
| 7. Порты | Go сам слушает PORT и отдаёт HTTP/REST, UI, health endpoints и метрики. Внешний веб-сервер для запуска не требуется. |
| 8. Параллелизм | API и worker запускаются независимо. Версии счетов и транзакции защищают от конкурентных изменений. Защита реализована условием обновления по версии и транзакциями; автоматические тесты временно удалены. Для нескольких API нужен балансировщик и изменение фиксированного host port в Compose; сам балансировщик пока не включён. |
| 9. Одноразовость | SIGINT/SIGTERM инициируют ограниченное по времени завершение HTTP и worker, затем flush трейсов. Миграции не выполняются внутри запуска API. Незавершённая проверка срока будет повторена следующим worker. |
| 10. Сходство окружений | Локальное окружение использует PostgreSQL 17.9 и SQL-миграции из репозитория. Образ и схема предназначены для повторного использования в других окружениях; SQLite не используется. Реального production-развёртывания пока нет. |
| 11. Логи | zap пишет JSON в stdout; приложение не открывает и не ротирует лог-файлы. Alloy собирает Docker logs, Loki хранит, Grafana показывает. trace_id/span_id/request_id связывают записи с запросами. |
| 12. Административные процессы | `payments migrate` — отдельный разовый процесс из того же образа и с той же конфигурацией базы. Миграции транзакционны, сериализуются advisory lock и проверяются по checksum. |
